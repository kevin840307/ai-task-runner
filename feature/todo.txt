0. 不可違反的設計原則
----------------------

[ ] 保留目前 AI Task Runner 的 UI 視覺語言，改善原有介面，不另造一套陌生的 ChatGPT 外殼。
[ ] Chat 負責對話、排隊與釐清；Task 負責工作紀錄；Runner Core 負責執行、Stage 路由、Retry、Recovery、Resume 與真實 Runtime 狀態。
[ ] Chat 不能因一般對話而偷偷建立或啟動 Runner Task。
[ ] UI、CLI、YAML、API、Dry Run 必須共用同一份核心契約，不可各自實作第二套排程或復原邏輯。
[ ] Task Draft 是暫存規劃資料，不是已建立 Task，也不能帶入假 Runtime / 假執行結果。
[ ] 一般 TaskDraft / Create Task 建立後進入 New / idle；只有使用者明確輸入 @goal 時，才允許以單一明確動作 Create + Run，且必須沿用同一 Runner action contract。
[ ] Main workspace 永遠保留；Worktree 是可選的隔離策略，不是另一套 Runner。Task-level Auto / Main / Worktree 必須共用同一 Workspace resolver；Global Auto workspace policy 只決定 Auto 的解讀。
[ ] Task 完成不代表自動 Merge。Git 整合是使用者明確執行的另一個動作。
[ ] 無法使用的按鈕必須 disabled 並說明原因；Backend 仍要再次驗證，不能只依賴 UI。
[ ] 避免 Dialog 疊 Dialog、俄羅斯娃娃式流程與重複資料副本。
[ ] 優先處理 24H 無人值守可靠性、恢復能力與可診斷性，不為 UI 功能另造 Scheduler / Recovery Engine。

[ ] 點擊左側 Project：選取該 Project 並直接進入該 Project 的 Chat。

[ ] Chat history 與 Task runtime history 分開儲存與顯示。

6. Chat Queue（對話排隊）
-------------------------

[ ] Queue 與 Runner Task List 是完全不同的概念；Chat Queue 只保存尚待送給目前 Chat Agent 的 Prompt。
[ ] Queue 以 Chat session 為單位儲存，切換 Project / Chat 不可串錯。
[ ] 有 Agent turn 執行中時，使用者送出的後續 Prompt 應依 Agent 原生能力加入 Queue；若 Agent 沒有原生 Queue，Backend 提供相同產品契約。
[x] Queue 項目直接顯示在 Composer 上方；沒有項目時整塊隱藏，busy 時另顯示自動排隊提示。
[ ] 每個項目顯示順序、可閱讀的摘要與 Edit / Delete。
[ ] Edit 使用 inline editor 或精簡的同一區塊，不再開一個大型 Modal；Save / Cancel 都要有效。
[ ] Queue 項目不能為空；儲存失敗時顯示明確錯誤並保留原值。
[ ] 預設 FIFO，除非 Agent 原生介面明確提供不同順序契約。
[ ] 以 Qwen Code 原生 queued-next-turn 行為為參考（例如 Ctrl+Q）；由 adapter 決定是否支援原生快捷鍵。
[x] Prototype 不提供 Queue 按鈕；Mock 模擬 Agent busy，連續按傳送會自動排隊，並可編輯／刪除多筆 Queue。Ctrl+Q 只保留為 busy 時的可選快捷鍵。
[ ] Mock 支援新增多筆、編輯、取消編輯、刪除、空白驗證、長訊息、切換 Chat session。
[ ] Backend 擁有 Queue 的真實順序、持久化與出隊狀態；UI 只顯示 Backend projection。
[ ] Agent 取消、session 過期、API 錯誤或使用者重啟後，不得無聲遺失未處理 Queue 項目。
[ ] 定義 Queue item 狀態（至少 queued / dispatching / completed / failed / cancelled），避免 UI 自行猜測是否已送出。


7. AI Ask / Clarification（反問使用者）
--------------------------------------

[ ] Ask 指的是 Agent 在目前工作過程中遇到需要使用者決定的事項，暫停目前 turn 並向使用者提問。
[ ] Ask 不是 Qwen /btw 這種獨立 side question；/btw 保持為 Agent 原生能力。
[ ] 統一 Ask 問題資料格式，避免 Qwen 與 OpenCode 各做一套前端流程。
[ ] 一次 Ask 可以有多個問題；每題可為選項題或自由文字題。
[ ] 選項題最後固定提供「其他／自行輸入」，選擇後顯示文字輸入框。
[ ] 選項題未選選項、Other 沒填文字、文字題空白時，不可 Next / Submit。
[ ] 每題顯示目前進度；使用者回答後按 Next；最後一題顯示 Submit。
[ ] Submit 將所有答案組成一份結構化 answers object，回傳給原本等待中的 Agent tool call，然後續跑同一個 turn。
[ ] Cancel 必須回覆明確的 cancel / deny 給待處理的 Agent question，不能捏造答案，也不能讓 turn 永久掛起。
[ ] 正式版 Ask 卡片嵌入 Chat 訊息流，選項清單有獨立捲動區，不使用遮住訊息的浮層。
[ ] Ask 是否可用由 Agent capability 決定；不支援時隱藏或 disabled，並說明原因。
[ ] OpenCode adapter 對應原生 question tool 的 header / question / options / custom answer 與多題 Submit 行為。
[ ] Qwen Code adapter 對應 ask_user_question 的 questions[] 與按索引對應的 answers；若當前版本能力不同，依實際 Agent contract 調整。
[ ] Ask request 綁定目前 Chat session、Agent turn 與 request ID，避免使用者切換 session 後答案送錯 turn。
[ ] Prototype 的一般訊息可以隨機觸發 Ask；Ask mock 按鈕 / @ask-demo 可以強制觸發，不依賴機率。
[ ] Mock 至少覆蓋：多選項題、文字題、Other 自訂答案、Next、最後 Submit、Cancel、空白驗證、切換 Agent / session。
[ ] 測試切換 Other 時要清掉舊答案；再次點擊已選 Other 不應意外刪掉已輸入文字。
[ ] 正式版需處理等待中的 Ask timeout、Agent turn cancel、session reconnect 與重送答案的冪等性。

9. @task / @task-single / @task-list 與 TaskDraft
-----------------------------------------------

[ ] 只有明確的 Runner 指令才可建立 TaskDraft；一般訊息提到 task / run / 建立任務不得觸發。
[ ] @task <spec>：由 AI 判斷產生單筆 Task 或多筆有序 Task List。
[ ] @task-single <spec>：強制產生且只產生一筆 Task。
[ ] @task-list <spec>：強制產生至少兩筆有序 child Task。
[ ] 三種命令共用同一個 Backend endpoint / service、固定 Prompt、TaskDraft schema、驗證與 Create 流程；只有 mode 參數不同（auto / single / list）。
[ ] 固定的 Generate Task Prompt 放在 Backend，參照既有 Generate Workflow 的做法；不可把整段 Prompt 寫死在瀏覽器。
[ ] Prompt 必須要求 AI 輸出結構化資料，不可以只回傳自由文字；驗證失敗要 fail closed。
[ ] 產生結果先顯示精簡 Draft 預覽，使用者可 Edit、Create Task 或 Dismiss。
[ ] TaskDraft 最低欄位包含 title、Project reference、ordered items[]；每個 item 至少包含 title、task prompt、Workflow、Project、workspace policy。
[ ] Validator / Prompt source override 只在需要時加入；不把無關 runtime 欄位塞進 Draft。
[ ] Draft 不包含 Runner runtime、Retry、Recovery、Merge 狀態；不得在建立前寫入正式 Task history。
[ ] 單筆 Draft 的 Edit 使用既有 canonical Task Editor。
[ ] 多筆 Draft 的 Edit 使用既有 Task List workspace；每個 child 的 Add / Edit 繼續使用同一個 canonical Task Editor。
[ ] 不新增 Chat 專用 Task 編輯表單；不要同步兩份平行 Draft state。
[ ] 從 Chat Draft 進入編輯時，Task Editor 必須是 viewport 上層的右側 overlay；Chat 留在背景、不縮窄、不位移。
[ ] 單筆 Editor 的 Back / Cancel / 遮罩關閉回到原 Chat Draft。
[ ] 多筆 Task List 關閉回到原 Chat Draft；從 List 進 child Editor，Back 先回 List，關閉 List 再回 Chat Draft。
[ ] 由 Task Info 進入 Add / Edit 時 Back 回 Info；由 Task List 進入時 Back 回 Task List。返回目的地由來源狀態決定，不可一律回 YAML。
[ ] Create Task 前再次驗證 items 不為空、Prompt / Project / Workflow / workspace policy 合法。
[ ] Create Task 後產生持久 Task ID、狀態 New、runtime idle；建立後不自動 Run。
[ ] Draft 失敗、格式不合法、缺欄位、空 Prompt、Backend 503 / timeout 時顯示可理解錯誤，且錯誤框不能被 modal、drawer 或 Composer 遮住。
[ ] Create / Dismiss / Retry / Edit / Back / Create Again 必須有明確的重複操作語義；不能重複建立同一 Draft。
[ ] Prototype 的 @task 隨機單筆 / 多筆；測試可使用固定 fixture / seed，避免自動化測試被隨機結果影響。
[ ] Prototype 保留 @task mock:error 與 @task mock:invalid 路徑，驗證 Backend error / schema validation UX。
[ ] 長 spec、含多行、含 bullet list、含特殊字元、Project 不存在、Worktree 不可建立都要有測試。
[ ] Mock request / response 必須與正式 API 共用同一份 TaskDraft schema，不可另造 mock-only model。


10. Task、Task List、狀態與編輯政策
---------------------------------

[ ] 一個 Board Task 可以有一個或多個有序 child Task；Task List 是父 Task 的 items[]，不是第二個 Scheduler。
[ ] New / Ongoing / Paused / Closed 是 Board lifecycle；Running / Recovering / Stopped / Completed 等是 Runner runtime projection。
[ ] Ongoing 不允許 New Task / Add Task / 編輯會改變 runtime 的內容；不合法動作需 disabled 並說明先 Pause。
[ ] 已完成 child 不可修改；Paused 時只允許依目前編輯政策修改合法項目。
[ ] Task List child 的新增、編輯、刪除、排序與 YAML 必須使用同一份 canonical items[]。
[ ] Edit Task 的 Back 依來源回 Info / Task List / Chat Draft；關閉按鈕、Cancel、Escape 與遮罩關閉行為需一致。
[ ] Delete Task 前顯示確認視窗，指出 Task ID、名稱、Project 與刪除後果。

[ ] 刪除正在執行、Recovering、或有不可安全刪除狀態的 Task 時必須阻擋，並顯示原因。

11. Workspace / Worktree
------------------------

[ ] Workspace policy 支援 Auto / Main / Worktree。
[x] Prototype 的 Auto 已改成讀 Global Auto workspace policy；所有已知 Run 入口共用 prepareTaskWorkspaceForRun / resolveTaskWorkspace。
[ ] 正式版 Global Auto policy 至少支援 busy→worktree / main-only / always-worktree，並由同一 Backend resolver 決定。
[ ] main-only 且 Main busy 時必須阻擋 Run；不可偷偷建立 Worktree。
[ ] always-worktree 時，即使 Main idle，Auto 也應建立 Worktree。
[ ] Main workspace 永遠可選；若同一路徑已有另一個 Task 在執行，禁止同一路徑第二個 Task 同時執行。
[ ] Auto：Main 可安全使用時走 Main；Main 被其他 Task 占用時依策略建立 Worktree。
[ ] Worktree 必須有醒目的 WORKTREE badge / banner、Branch、Execution Path、隔離提示；不可只藏在 Info 欄位。
[ ] 每個 child Task 可以有自己的 Workspace policy；Task List 的多筆 Task 不可錯把全部當成同一個工作目錄。
[ ] Worktree 建立前檢查 Git repository、branch 名稱、path、權限、磁碟空間與既有 worktree；失敗時不建立半成品。
[ ] Workspace resolver 是唯一決定 Project path / Main path / Worktree path 的來源；UI 不自行拼出正式路徑。
[ ] Backend 對 path 做正規化與保護，避免 path traversal、跨 Project 寫入與錯刪資料夾。
[ ] Stop / Resume / Restart / process recovery 必須保留 Workspace identity；不能 Resume 到另一個路徑。
[ ] Task 刪除、Task reset、Run 完成與 Worktree 清理政策分開；不能默默刪掉尚未 Merge 的修改。
[ ] 平行 Agent 仍使用 Worktree 做隔離；不以多個 Agent 直接同時寫同一份 working tree 取代隔離。


11. Workspace Results 與 Merge
-------------------------------

[ ] Merge UI 依 Project 分組列出 Worktree / branch 結果，而不是每個 child Task 各自產生一套互相重複的 Merge 面板。
[ ] 每個結果清楚顯示 Project、來源 Branch、來源 Path、目標 Branch、Task / Task List、最近狀態與衝突摘要。
[ ] Merge 面板只提供兩個主要動作：Merge、Merge Chat。
[ ] Backend 先做 merge preflight / conflict check；不能只依前端 Mock 狀態判斷。
[ ] 無衝突且檢查通過：允許 Merge，顯示確認與結果；不自動執行。
[ ] 有衝突：直接 Merge disabled，只能 Merge Chat。
[ ] Merge Chat 建立該 Project 的新 Chat session，預填完整 prompt，但絕不自動送出。
[ ] Merge Chat prompt 包含來源 Worktree path、來源 Branch、目標 Project path / target branch、衝突檔案摘要、要求先檢查差異再安全整合的指示。
[ ] 多 Task / 多 child 產生同一 Worktree 時，應以實際 Workspace / branch 為整合單位去重，避免每個 child 重複 Merge 同一 branch。
[ ] 同 Project 不同 Worktree 的結果要分開顯示；不允許把不同 branch 當成一筆。
[ ] Merge 完成後保存結果、commit / merge reference 與錯誤；UI 更新 Workspace Results。
[ ] 不因 Task Closed 自動 Merge；不新增 Waiting Merge / Merged / Cleanup 等 Board 欄位。
[ ] Merge Chat 只建立新 Chat session 與預填內容；不得偷送訊息或自動啟動 Task。
[ ] Merge 失敗時保留 Worktree / branch 與變更；不可自動清除使用者的未整合修改。


12. 共用 Chat Backend 與 API
---------------------------

[ ] Chat 必須共用既有 Backend server / process manager / 設定載入 / logging / auth 與 error handling；不再起一個平行的獨立 Chat Backend。
[ ] 新增 Chat service layer，負責 Session、Message、Stream、Queue、Ask、Agent capability 與 TaskDraft generation 的 API 協調。
[ ] Chat 不直接執行 Runner workflow；要執行時由明確的 Task Create / Run API 進入既有 Runner。
[ ] 對外 API 命名可依現有專案慣例調整，但能力至少包含：
    - 取得 / 建立 / Rename / 切換 / 刪除 Chat session
    - 取得訊息歷史、送出訊息、取消目前 turn、重新連線
    - Project-level Agent / Model / Mode / Workflow capability 與目前選擇
    - 取得 Agent commands / Skills / permission / Ask capability
    - Queue list / enqueue / edit / delete / reorder（若產品允許排序）
    - Ask request event / answer submit / cancel
    - generate TaskDraft / validate TaskDraft / create Task
    - Merge preflight / direct merge / Merge Chat handoff context
[ ] 所有 API 使用穩定的 session_id、turn_id、message_id、queue_item_id、ask_id、draft_id、task_id。
[ ] POST / send / create 等操作需要 request ID 或 idempotency key，避免重試後重複建立訊息或 Task。
[ ] 使用 SSE / WebSocket 或專案現有 streaming 機制回傳事件；不建立第二套長連線管理器。
[ ] 定義統一事件：message_delta、message_completed、tool_started、tool_completed、queue_updated、ask_requested、ask_resolved、turn_completed、turn_failed、capabilities_updated。
[ ] Chat stream 與 Runner Task runtime stream 必須明確分開；不能混用 Task Stage event 代表 Chat tool call。
[ ] API error 回傳可辨識的 code、message、retryable、request_id；UI 依 error code 顯示可操作錯誤。
[ ] API 支援 cancel、timeout、disconnect / reconnect、session expiration 與重送保護。
[ ] Chat history、Queue 與等待中的 Ask 有清楚的持久化策略；重啟後不可以讓 UI 顯示假的執行中狀態。
[ ] 不把完整 system prompt、憑證、API key 或敏感本機環境資訊回傳給 UI。
[ ] API contract 要有 unit / integration test 與最小可讀文件；UI Mock 與正式 API 共用 schema。


14. Agent Adapter
-----------------

[ ] 定義一個統一 AgentAdapter 介面；Qwen Code 與 OpenCode 都實作同一份產品契約。
[ ] Adapter 需負責：啟動 / 連線、傳送訊息、stream 解析、cancel、Model 列表、Mode mapping、Commands / Skills discovery、Ask、Queue capability 與錯誤正規化。
[ ] Agent 原生能力不可用時，回報不支援；不要在 UI 假裝可用或以不同語義硬模擬。
[ ] Qwen Code adapter 必須參照目前安裝版本的 CLI / SkillManager / slash command registry；不能假設不同版本的內部 API 不變。
[ ] OpenCode adapter 必須參照目前安裝版本可用的 server / SDK / command / skill registry；不能只解析 console output 當成正式 API。
[ ] 盡可能重用既有 Agent CLI process / Backend session 管理，不為每個 UI 下拉另啟一個 CLI。
[ ] Model 列表與預設值由 Adapter 回傳；不要在 production frontend 硬編碼模型名稱。
[ ] Mode profile 是產品層抽象；Adapter 回報 native mapping、支援狀態與安全描述。
[ ] Ask 使用統一的 normalized question schema；Adapter 把 Qwen ask_user_question / OpenCode question tool 映射到該 schema。
[ ] Queue 優先使用 Agent 原生 queued-next-turn；無原生能力時由共用 Chat service 提供 FIFO Queue。
[ ] Slash skill 只顯示 Agent 實際解析且允許使用的能力；保留原生權限與 user-invocable 限制。
[ ] Adapter 具備 timeout、cancel、child process cleanup、stderr / bounded logs 與 reconnect / restart 行為。
[ ] 針對 Qwen / OpenCode 分別測試：Model 取得失敗、skill registry 失敗、Agent 不支援 Ask、permission denied、CLI 版本不相容。


15. Runner 必要變更
-------------------

[ ] Runner Core 仍是唯一執行入口；Chat service 不複製 FlowEngine、StageExecutor、retry / recovery / resume 或 Task lifecycle。
[ ] 新增正式 TaskDraft schema 與 validator，將 AI 回應轉為既有 canonical Task / RunRequest 資料。
[ ] 新增共用 generate-task service：輸入 spec、Project context 與 mode（auto / single / list），後端套用固定 Prompt，輸出 TaskDraft。
[ ] Generate Task 的固定 Prompt 參照 Generate Workflow 現有模式，但不得複製一套 Workflow Generator runtime。
[ ] AI 輸出解析、schema validation、Project / Workflow / Prompt / Validator / Workspace 驗證由 Backend 執行；無效輸出 fail closed。
[ ] TaskDraft Create 必須呼叫既有 Task 建立服務；不在 UI 直接寫正式 Task store。
[ ] 建立 Task 時使用既有 durable Task ID、History、Project identity、Workspace resolver 與狀態轉換。
[ ] TaskDraft / Create Task 建立後只進 New / idle；@goal 是另一個明確 command，可在同一 Backend service 中完成 Create + Run。
[ ] 同一路徑只能有一個 Task 同時處於執行中；檢查必須在 Backend / Runner，不可只做 UI disabled。
[ ] Task List 的 child 仍依現有 RunRequest / FlowEngine 依序執行；不新增平行 Task scheduler。
[ ] UI 不得直接修改 runtime truth；Stop / Resume / Restart / Close 都呼叫既有 Runner action API。
[ ] Ask 發生時，Agent turn 需有明確的 pending-question 狀態與 ask_id；Submit 後回傳結構化答案並繼續原 turn。
[ ] Ask Cancel / timeout / client disconnect 要明確終止或取消等待狀態，避免 runner / agent process 永久卡住。
[ ] Queue 項目只由 Chat service / AgentAdapter 排隊，不混入 Runner Task List。
[ ] Agent tool permission / YOLO 設定由 Adapter / Backend 生效；不可只在前端顯示模式。
[ ] Workspace path、Worktree 建立、Git preflight、Merge 都走共用的 Backend service；不可讓 UI 自行組路徑或執行 Git。
[ ] Merge preflight 與 direct merge 必須有安全檢查、lock、結果紀錄與可重試錯誤；衝突時拒絕 direct merge。
[ ] Task reset、delete、run history 與 Worktree cleanup 的生命週期分開處理。
[ ] 確保 Chat API 故障不影響正在跑的 Runner Task；Chat server 重啟不得清除或破壞 Runner recovery state。
[ ] 所有新服務加入 bounded logs、request correlation ID、明確 timeout 與 deterministically testable return values。
[ ] 若要修改 Runner runtime contract，先補文件與測試，再接 UI；不要只用 Prototype 行為當作契約。


16. 測試策略與驗收

[ ] 單元測試：TaskDraft parser / schema / mode 約束 / 空白 prompt / 多筆排序 / workspace policy。
[ ] 單元測試：AgentAdapter capability mapping、Model / Mode 相容性、Ask schema、Queue FIFO / idempotency。
[ ] API 測試：Chat session CRUD、訊息串流、cancel / reconnect、Queue edit/delete、Ask submit/cancel、TaskDraft create。
[ ] Browser 測試：Project 點擊進 Chat、Project-level Agent/Model/Mode/Workflow、@ / 提示、TaskDraft Edit / Back / Create、Queue、Ask、錯誤框。
