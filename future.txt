AI Task Runner - Future Direction
=================================

Updated: 2026-10-18
Migration baseline: main @ b5239e3a5a3c4fe1f900c443e8d4bbcd300611ca
UI/UX target reference: feature/ui prototype + 2026-10-18 latest decisions

PURPOSE
-------

This file defines the target product direction for evolving the current main branch.
It is not a second Runner/runtime contract and it is not a record of prototype completion.

Precedence when sources disagree:

1. current main runtime contracts and proven reliability behavior;
2. latest decisions in this document and feature/git-worktree-todo.md;
3. feature/ui prototype behavior/commit history as UI/UX reference;
4. older future/todo/prototype wording.

The prototype demonstrates interaction and layout direction only. Production implementation must
reuse current main owners, APIs and tests instead of copying prototype mocks or reintroducing old contracts.


CURRENT MAIN BASELINE - KEEP, DO NOT REDO
=========================================

Runtime
-------
- WorkflowRunner remains the composition/entry owner.
- FlowEngine remains semantic PASS/FAIL/HANDOFF + dynamic child Workflow owner.
- StageExecutor remains technical retry/session/recovery/timeout/safety owner.
- RunState/StateStore remain durable runtime truth.
- Dynamic Handoff remains supported; Discussion/Group Chat remains removed.
- YAML remains canonical for Workflow definitions.
- ERROR is technical and is not a graph edge.
- Existing resume/recovery/process-restart/API transient recovery behavior must not regress.
- Existing 24H/live/dry-run reliability evidence is the baseline to preserve.

Runner API boundary
-------------------
- Runner is driven by project_root and task/workflow inputs.
- CLI/standalone Runner remains independent from future UI workspace/worktree orchestration.
- Do not make Runner understand UI Task board state, Chat session state, Git branch/worktree state,
  merge queues, merge failure counters or Project Chat history.

Existing runner/workspace.py
----------------------------
- runner/workspace.py already owns Runner-side project safety/instruction/read-only helper behavior.
- It is NOT the future Git-worktree orchestration package.
- Do not move Git worktree/merge ownership into runner/workspace.py merely because the names are similar.

Current production UI / Studio
------------------------------
- Preserve the current visual language, theme tokens, accessibility baseline and layout conventions.
- Preserve current Workflow/Prompt asset management and Full Designer.
- Workflow Studio source remains ui/studio-src; committed built output is generated artifact, not source.
- Preserve canonical runtime projection and server-side action guards already used by main UI.
- Preserve current backend/environment diagnostics behavior.

Backend/model discovery
-----------------------
- main already has registry/adapter-driven backend/model discovery.
- Qwen/OpenCode model discovery fixes in current main are baseline behavior.
- New Chat/Task UI must consume the existing backend catalog owner; do not reimplement model lists in frontend.
- Provider-specific discovery remains adapter-owned.


1. PRODUCT SHELL / NAVIGATION
=============================

1.1 Main surfaces
-----------------
Target primary surfaces:

- Project Chat
- Tasks
- Workflows
- Prompts

Keep the existing product visual style. Do not replace it with a generic ChatGPT clone.

1.2 Project navigation
----------------------
- Project is the primary working context.
- Clicking a Project selects it and opens that Project's Chat.
- Project "..." is management only (Rename/Delete/etc.) and must not navigate.
- Project list remains independently scrollable.
- Project identity is path/id based; rename changes display name, not references.
- New Project initialization uses one backend owner for Project defaults/settings.

1.3 Tasks page filtering
------------------------
- Tasks Project filter is page-local and does not switch the active Project Chat.
- Parent Task Lists remain visible when any child matches the selected Project filter.
- Search/running filters must not mutate the global selected Project.

1.4 Workflows / Prompts
-----------------------
- Keep current main Workflow/Prompt Studio and asset ownership.
- Task/Chat may link to these assets but must not create another editor or asset store.
- "Open Workflow" is only enabled when a concrete selected Task item has a Workflow.


2. GLOBAL SETTINGS / PROJECT PREFERENCES
========================================

2.1 Global Settings location
----------------------------
- Global Settings lives at the bottom of the left sidebar.
- Remove the old standalone theme button after the Settings replacement is production-ready.
- Use one Settings shell, not separate unrelated settings dialogs.

2.2 Interface
-------------
Global Interface settings:
- Appearance: System / Light / Dark
- Theme palette: Teal / Deep Blue / Violet / Amber / Rose
- Motion/accessibility preferences when already supported by main

Use current main theme tokens. Do not copy prototype CSS as a second theme system.

2.3 Language
------------
- Language is a dedicated Global Settings section.
- zh-TW / English are the initial supported UI choices.
- Production i18n uses the existing UI translation owner.

2.4 Global Defaults
-------------------
Global Defaults provide initial values for newly created Projects:
- Agent
- Model
- Mode
- Reasoning
- Workflow

Defaults are copied when a Project is created. Changing Global Defaults must not silently rewrite
existing Project preferences.

2.5 Project preferences
-----------------------
Each Project owns:
- Agent
- Model
- Mode
- Reasoning
- Workflow

All Chat sessions under the same Project share these preferences.
Creating/switching Chat sessions does not reset them.

Prototype reasoning values may be used for UI reference, but production supported reasoning levels
must be returned/mapped by the selected Agent/backend rather than assumed universally.

2.6 Execution settings
----------------------
The final target also includes:
- Auto workspace policy
- Merge failure limit
- Allow concurrent Main tasks

These settings belong to the future Git-worktree phase and must not become active/dead controls before
the production workspace backend exists. Their authoritative final semantics are defined in
feature/git-worktree-todo.md.


3. NORMAL PROJECT CHAT
======================

3.1 Chat is not Runner Task execution
-------------------------------------
- Normal Project Chat is an engineering conversation.
- Sending a normal Chat message must not silently create/start a Runner Task.
- Current Runner messages/runtime history must not be reinterpreted as ordinary Chat history.
- New Chat persistence is separate from Runner RunState/runtime logs.

3.2 Chat sessions
-----------------
- A Project can have multiple Chat sessions.
- Create / rename / switch / delete are Project-scoped.
- Session messages, Queue and pending Ask state are Chat-session scoped.
- Project Agent/Model/Mode/Reasoning/Workflow preferences are Project scoped.
- Delete Chat requires confirmation and must not affect Runner Task history.

3.3 Composer
------------
- Compact by default.
- Auto-grows vertically to a bounded max height, then textarea scrolls.
- Message area must keep the last message visible as Composer grows.
- Programmatic prefill recalculates height immediately.
- Mode remains a compact quick control.
- "+ New Task" sits near the Composer controls and creates a Task/Task List for the current Project.
- Do not show the redundant Project tag under the Composer.

3.4 Chat settings
-----------------
- Workflow / Agent / Model / Reasoning live in compact Chat settings.
- Mode remains quickly accessible.
- Opening Chat settings must not reflow or shrink the Chat surface.
- Model choices reuse main's backend/model catalog.
- Agent changes refresh dependent Model/Mode/capability data; Reasoning follows the Project preference unless
  capability mapping requires normalization.


4. AGENT CAPABILITIES / COMMAND DISCOVERY
=========================================

4.1 @ namespace
---------------
At Composer start:
- @goal
- @task
- @task-single
- @task-list
- other Runner-owned system commands/prompts as explicitly supported

Selecting a suggestion inserts it; it does not auto-send.

4.2 / namespace
---------------
"/" lists the selected Agent's user-invocable commands/skills.
Frontend does not scan arbitrary skill folders or hardcode installed skills.

A normalized capability projection should include enough data for:
- token/name
- description
- kind
- source
- enabled/availability
- permission/user-invocable state

Agent-specific discovery stays behind adapters.

4.3 Existing model catalog reuse
--------------------------------
- Do not rebuild Qwen/OpenCode model discovery.
- Extend around the current main backend catalog only where Chat needs additional capability metadata.
- Avoid turning the existing Runner BaseBackend into a Chat-session God object; a thin interactive adapter/service
  may reuse backend discovery without contaminating Runner RunState.


5. CHAT QUEUE
=============

- No dedicated "+ Queue" button is required.
- If an Agent turn is active and the user sends another normal Chat message, it becomes queued automatically.
- Multiple queued messages are supported.
- Queue appears above the Composer.
- Queued items can be edited or deleted before execution.
- FIFO ordering is preserved.
- Queue state is Chat-session scoped.
- Pending Ask blocks continuation of the active turn; newly sent messages remain queued until Ask resolves/cancels.
- Queue is a Chat concern and must not become a Runner Task scheduler or FlowEngine queue.


6. AI ASK / CLARIFICATION
=========================

- Normalize Agent-specific ask/question tools into one Chat Ask projection.
- Ask renders as an interactive card inside the Chat message stream.
- No production "Ask mock" Composer button.
- Support multiple questions per Ask request.
- Question types:
  - option selection
  - option + final Other/custom text
  - free text
- Extra context is optional.
- Next advances question-by-question; final Submit returns structured answers.
- Cancel explicitly cancels/denies the pending Agent question; do not invent an answer.
- Long option sets remain usable without covering the Composer.
- Ask state is scoped to the Chat session/turn, not Runner retry/recovery.


7. TASK GENERATION FROM CHAT
============================

7.1 @task commands
------------------
- @task <spec>: backend decides one Task vs ordered Task List.
- @task-single <spec>: exactly one Task.
- @task-list <spec>: ordered multi-Task list.
- No dedicated @task button.
- Ordinary Chat text must not be guessed as Task creation intent.

All three use one backend TaskDraft generation service with a mode constraint:
- auto
- single
- list

7.2 TaskDraft
-------------
TaskDraft is transient planning data, not a durable Task and not fake runtime state.

Minimum concept:
- title
- current Project reference
- ordered items[]
- per item: title/spec, Workflow, Project, execution options
- optional prompt/validation/file inputs when required

Chat shows only a compact preview:
- Edit
- Create Task
- Dismiss

Edit reuses the canonical Task Editor / Task List Drawer. Do not build a second Chat-only Task form.

Create Task creates New/idle only. It does not automatically Run.

7.3 @goal
---------
@goal is the explicit fast path for Create + Run.
It must still:
- create a durable Task first;
- use the same Task schema/default resolution;
- use the same backend Run action/guards;
- appear in Tasks/Ongoing;
- never be inferred from ordinary Chat text.


8. TASK PRODUCT MODEL
=====================

8.1 Durable Task
----------------
- Task is a durable work record, not the current worker process.
- Old/Closed Tasks remain visible until Delete.
- Runtime attempts/history attach to Task identity.
- Existing legacy Runner run history must remain inspectable; do not fabricate old durable Tasks from it.

8.2 Board lifecycle
-------------------
Keep exactly:
- New
- Ongoing
- Paused
- Closed

Runtime/recovery/workspace detail is secondary state, not extra Board columns.

State changes/actions remain backend guarded.
UI disabling is UX only.

8.3 Board + List views
----------------------
- Tasks supports Board and dense List views.
- Cards/rows prioritize title/status/project/progress; long descriptions truncate with ellipsis.
- Drag/drop is preferred for Task List child ordering.
- Remove redundant Move Up/Move Down actions when drag reorder is available.
- Task state drag/transition must call canonical backend actions, never mutate frontend truth only.

8.4 Delete
----------
- Delete requires confirmation.
- Active/running/recovering Task delete is disabled and backend rejected.
- Delete removes Task product records/history references according to retention policy.
- Source-control integration is never hidden inside Delete.


9. ONE TASK DRAWER / TASK WORKSPACE
==================================

9.1 Single shell
----------------
Task details and editing use one right-side Task Drawer shell.
Do not stack large modal-on-modal flows.

The Drawer owns:
- Info shell with fixed tabs:
  - Overview
  - Runtime
  - Output
  - History
- Task List workspace
- Task Editor subview
- YAML subview

"Steps" is obsolete terminology and must not return as a separate tab/page.

9.2 Info
--------
- Info is inspection-first.
- Shows Task identity, Project, Workflow, runtime projection, progress, history and workspace/result detail.
- Open Workflow only when a selected item has one.
- Reset/Rerun/Resume actions use existing backend runtime/action guards.

9.3 New Task behavior
---------------------
- Clicking + New creates/opens a transient creation workspace, not a durable Task immediately.
- Opening Task List must not create a Task as a side effect.
- Create is enabled only when valid Task content exists.
- After successful Create, open the newly created Task Info.

For a New durable Task opened later, Task List is the default editable workspace; provide Back to Info.

9.4 Source-aware Back
---------------------
Examples:
- Info -> Add/Edit child -> Editor -> Back to Info/Task List as appropriate
- Task List -> Editor -> Back to Task List
- Chat TaskDraft -> Editor/List -> Back to Chat Draft

Do not hardcode all Back actions to the same destination.

9.5 Dirty-state ownership
-------------------------
- Task Editor and YAML have local unsaved snapshots.
- Back / X / Escape / navigation must confirm before discarding.
- Child Editor dirty state is resolved before discarding a parent Task List Draft.
- Escape is owned by the top-most active layer; child picker/context/confirm dialogs handle it before Drawer close.
- Restore focus to the initiating control after close/cancel where practical.


10. CANONICAL TASK EDITOR
========================

One Task Editor markup/controller is reused by:
- New Task
- existing Task edit
- Task List child Add/Edit
- Chat TaskDraft single edit
- Chat TaskDraft list child edit

Do not fork forms by entry point.

Layout target:
- compact Project + Workflow + optional Title basics row
- Task Prompt is primary visual surface
- File Validator / AI Validation shown only when required/configured
- Workspace/execution settings remain secondary
- source mode selectors keep stable horizontal geometry
- mixed File Validator + AI Validation cards align consistently
- narrow view falls back cleanly without changing the field model

Task execution selectors reuse common catalogs/preferences:
- Agent
- Model
- Mode
- Reasoning
where Task-level override is supported by the final backend contract.


11. TASK LIST / YAML
====================

- Reuse the existing ordered YAML/CLI task capability; do not build another scheduler.
- One parent Task owns ordered child items.
- Task List owns list identity/order; child Project/Workflow/Prompt/validation/execution settings stay on each child.
- Child Add/Edit reuses the canonical Task Editor.
- YAML is an advanced view of the same Task List model.
- YAML edit has Validate / Apply and dirty-discard protection.
- New/Ongoing/Paused/Closed mutation rules prevent rewriting completed execution history.
- Ongoing is observation-only.
- Paused may allow only safe future/current edits according to restart semantics.
- Closed is read-only except explicit lifecycle actions.


12. TASK FILE INPUT / UPLOAD CONTRACT
=====================================

For Task goal/prompt file, File Validator and AI validator prompt file where upload is supported:

- UI action is Upload file, not a fake path-only browser chooser.
- Browser-selected file is staged transiently.
- Backend returns/displays a full managed destination path in the same Task path field.
- Create/Save atomically copies/materializes the staged bytes to the managed Task location.
- Canonical Task data stores the managed path, not Browser File objects or fakepath.
- If the user manually edits the path field, manual path wins and staged upload for that field is discarded.
- Copy failure fails closed; never persist a Task pointing at a missing staged file.
- TaskDraft and Task List editing preserve staged upload state until Create/Save or explicit discard.


13. BACKEND / DATA OWNERSHIP
============================

13.1 Chat service
-----------------
Add one shared backend/service boundary for:
- Project Chat sessions/messages
- active turn status/stream
- Queue
- pending Ask
- TaskDraft generation

Do not route ordinary Chat through FlowEngine/StageExecutor merely to reuse execution code.

13.2 Task service/store
-----------------------
One backend owner for:
- durable Task / Task List records
- lifecycle/status
- ordered child items
- source-aware editor data
- Task -> Runner run requests
- allowed actions

Do not use frontend/localStorage as production Task truth.

13.3 Preferences/settings
-------------------------
One backend/config owner for:
- Global Settings
- Global Defaults
- Project preferences

Prototype localStorage behavior is not the production owner.

13.4 Runtime projection
-----------------------
Reuse main's Runner-owned runtime projection/action guards.
Task Info consumes this projection; it does not derive a second runtime state machine.

13.5 Existing Runner files
--------------------------
Do not overload runner/workspace.py with future Git worktree orchestration.
Runner safety/project-instruction behavior stays Runner-owned.

16. FINAL DEFERRED PHASE: GIT WORKTREE / MAIN DELIVERY
======================================================

This is intentionally the last large feature phase after Chat/Task production migration is stable.

Detailed and authoritative contract:
    feature/git-worktree-todo.md

High-level target only:

Physical boundary
-----------------
- Add a NEW top-level workspace/ backend package for Git worktree/merge orchestration.
- Do not place it under runner/ or ui/.
- Do not confuse it with existing runner/workspace.py.
- Current UI/Task flow prepares a Task worktree first, then calls Runner(project_root=worktree).
- CLI/standalone Runner remains caller-project_root driven and worktree-unaware.
- workspace/ and Runner do not import each other's internals; Task Backend/Orchestrator coordinates them.

Modes
-----
- Auto
- Main
- Isolated Worktree

All current UI Task executions use isolated Task worktrees.
Mode controls delivery after Runner completion.

Main completion
---------------
- Runner Complete is not Main Task completion.
- Snapshot/commit the local Task result.
- Serialize delivery per repository + captured target branch.
- Direct normal merge uses the current merge source into the captured Project branch.
- Main becomes Closed only after merge commit succeeds.
- no_changes is the normal exception with nothing to deliver.

Merge/recovery
--------------
- Use ancestry-preserving direct merge, not old candidate/integration/squash designs.
- Keep merge abortable until required post-merge validation passes.
- Post-merge validation is needed when target moved beyond the base against which the current merge source was validated.
- Validation is verdict-only/source-non-mutating.
- Real source conflict/failure increments Task merge_failure_count.
- Read Global merge_failure_limit after each real failure.
- Within limit: create latest-target recovery workspace and call the existing Runner again.
- Recovery result becomes the new current merge source.
- Above limit: stop automatic Main delivery and retain latest result as Isolated Worktree / worktree_ready.
- Target/history/worktree ownership anomalies fail closed and do not become fake source failures.

Global Execution settings
-------------------------
- Auto workspace policy
- Merge failure limit
- Allow concurrent Main tasks

Concurrent Main allows parallel Runner execution in separate worktrees while same-target delivery remains serialized.

The root future.txt intentionally does not duplicate the full Git transaction contract.
When implementing this phase, feature/git-worktree-todo.md is the source of truth.


17. NON-GOALS
=============

- Do not redesign the proven Runner runtime to implement Chat/Tasks.
- Do not create a second Workflow engine, Runner, retry engine, recovery engine or runtime state store.
- Do not turn normal Chat into Runner execution.
- Do not create a separate Task scheduler when existing ordered YAML/CLI behavior is sufficient.
- Do not copy prototype mocks/hardcoded models/skills into production.
- Do not keep obsolete UI handlers after the replacement is covered.
- Do not restore old Git integration/candidate/squash contracts.
- Do not let Git worktree functionality leak into Runner/CLI contracts.


18. DEFINITION OF TARGET COMPLETE
=================================

The future migration is complete only when:
- main production UI matches the agreed Project Chat / Tasks / Drawer / Settings interaction model;
- normal Chat and durable Runner Tasks are separate but connected through explicit commands/actions;
- Project/Global preferences are backend-owned;
- Queue/Ask/capability discovery are production-backed;
- TaskDraft/Task Editor/Task List/YAML reuse one canonical product model;
- current Workflow/Prompt Studio and Runner reliability remain intact;
- browser/API/runtime regression gates are green;
- legacy replaced UI paths are removed;
- final Git worktree/Main-delivery phase is implemented and verified per feature/git-worktree-todo.md.
