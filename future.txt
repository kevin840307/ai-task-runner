AI Task Runner - Future Architecture
====================================

Purpose
-------
Keep one reliable runtime and let future workflow interaction models change only
routing semantics.

The user-facing contract stays:

  Chat / CLI / API
        ->
  select Workflow/Profile
        ->
  enter Prompt
        ->
  Run

Chat must not require a separate Linear / Dynamic / Discussion mode selector.
The selected Workflow/Profile carries its own routing/editor metadata.

Core design rule
----------------
Stage is the only execution unit.

Plan, Execute, Review, Validator, Command, Coder, Reviewer, Architect,
Researcher and Moderator are all Stages.

An Agent is not a second runtime abstraction. It is normally an AI Stage with
role / prompt / session_key / tools / safety configuration.

The runtime stays:

  WorkflowRunner
    |-- FlowEngine
    |    '-- RoutingStrategy
    |         |-- Linear
    |         |-- Dynamic
    |         '-- Discussion
    |
    |-- StageExecutor
    |    |-- technical retry
    |    |-- timeout
    |    |-- API transient recovery
    |    |-- same-session retry
    |    |-- fresh-session escalation
    |    |-- watchdog integration
    |    '-- safety/hooks
    |
    '-- StateStore
         |-- durable state
         |-- checkpoint
         '-- resume

Do NOT create separate full runtimes such as:
- LinearWorkflowOrchestrator
- DynamicHandoffOrchestrator
- GroupChatOrchestrator

Future strategies must reuse WorkflowRunner, StageExecutor, StateStore,
backend/session handling, protected-path safety, diagnostics and resume.

Target routing strategies
-------------------------

1. Linear Workflow with Rollback / Loop
   Current production strategy.

   Flow is declarative and inspectable:
   - next
   - restart_at
   - recover edge
   - repeat
   - max_attempts
   - on_exhausted
   - task scope
   - validation rollback

   Technical retry/recovery remains outside Linear routing.

2. Dynamic Handoff
   Future strategy.

   Multiple role-based AI Stages may hand work to another Stage at runtime.

   Example:

     Planner
        ->
     Coder
        ->
     Reviewer
        |-- code problem ------> Coder
        |-- architecture issue -> Architect
        |-- missing evidence --> Researcher
        '-- PASS -------------> Validator

   The Stage may return bounded structured routing intent, for example:
     target
     reason
     evidence/context reference

   FlowEngine validates that intent and the Dynamic RoutingStrategy decides the
   next Stage.

   Dynamic Handoff must not create its own retry/session/watchdog runtime.

3. Discussion / Group Chat
   Future strategy.

   Participants are still Stages.

   Example:

     Architect -> Coder -> Reviewer -> Security
              discussion round
                    |
              next round?
               /       \
             yes       no
              |         |
          next round   Judge
                         |
                      Execute

   Discussion-specific state may include:
   - round
   - active speaker
   - participant order/policy
   - bounded discussion summary
   - judge/moderator decision

   Raw transcript must remain bounded.

   Discussion must reuse the same Stage execution reliability and project write
   safety.

Shared runtime capabilities
---------------------------
The following are mode-neutral and must remain shared:

- StageExecutor
- backend/model selection
- AI session handling
- API transient classification
- same-session retry
- fresh-session escalation
- timeout
- watchdog
- process ownership
- subprocess cleanup
- protected-path / Git safety
- durable save
- checkpoint/resume
- bounded diagnostics/logging
- prompt/resource snapshots
- validators
- plugin/tool boundary

Mode-specific semantics
-----------------------
These belong to RoutingStrategy, not StageExecutor:

Linear:
- workflow_position
- task_step
- restart_at
- rollback
- recover edge
- repeat

Dynamic:
- current owner
- handoff target
- handoff budget
- allowed target policy

Discussion:
- round
- next speaker
- moderator/judge
- termination rule

State direction
---------------
Keep one authoritative durable RunState / state.json commit point.

Conceptually separate:
- common lifecycle
- Stage/session state
- latest transition context
- routing_state

Do not prematurely create three large state class hierarchies.

Future routing_state examples:

Linear:
  strategy: linear
  position: ...
  task_step: ...

Dynamic:
  strategy: dynamic
  current_stage: ...
  handoff_count: ...

Discussion:
  strategy: discussion
  round: ...
  active_speaker: ...

Only introduce structural schema migration after ownership is stable and resume
compatibility is covered by tests.

UI direction
------------
Use one Workflow/Profile catalog and preferably one Graph Designer.

Node:
  Stage

Edge:
  routing

Workflow/Profile metadata should eventually expose:
- id
- name
- routing_strategy
- editor_kind
- schema_version
- capabilities
- source/location

Chat remains:
  select Workflow -> Prompt -> Run

Editor behavior may vary by metadata:
- Linear: normal/restart/recover edges
- Dynamic: handoff targets / runtime dynamic edges
- Discussion: participant/group/round properties

Do not build three unrelated UI products unless real requirements prove it is
necessary.

Write ownership
---------------
Future multi-agent strategies must not allow uncontrolled concurrent writes.

Default rule:
- many Stages may read/reason/review;
- only one write owner per project/worktree at a time;
- handoff explicitly transfers write ownership;
- parallel writers require isolated worktrees plus controlled merge/reconcile.

Compatibility
-------------
- Existing Linear Workflow YAML remains valid.
- Existing Stage registry remains the execution catalog.
- execution_mode defaults to linear while the public compatibility field exists.
- YAML List remains Linear-only until a mode-aware batching contract is designed.
- Existing Chat/UI workflow selection remains unchanged.
- Old compatibility module/class names may remain as re-exports, but no new
  runtime behavior may be added to them.

Implementation order
--------------------

Current:
1. Finish Linear architecture cleanup.
2. Keep WorkflowRunner / FlowEngine / LinearRouting / StageExecutor boundaries.
3. Prove deterministic closure and resume equivalence.
4. Pass Windows + Ubuntu fast CI.
5. Pass real-Qwen closed-loop probes.
6. Pass 24H high-density soak.

Before the second routing strategy:
7. Define the smallest RoutingStrategy protocol from the real Linear code.
8. Add workflow/profile routing metadata used by runtime and UI.
9. Keep the same WorkflowRunner and StageExecutor.

Dynamic:
10. Implement one minimal Dynamic RoutingStrategy prototype.
11. Use existing AI Stage configurations for Coder/Reviewer/Architect roles.
12. Add bounded handoff state and deterministic simulation.

Discussion:
13. Build on the same Stage/runtime contract.
14. Add only discussion-specific round/speaker/termination state.
15. Add deterministic discussion simulation before live use.

Avoid premature abstractions
----------------------------
Do not introduce until real second-strategy requirements prove they are needed:
- UniversalAgent
- GenericEverything
- multiple full Orchestrators
- arbitrary expression language in edges
- unlimited DAG semantics
- large AgentMessage hierarchy
- separate runtime per interaction model

Final rule
----------
Workflow defines the work.
Stage performs one responsibility.
StageExecutor makes Stage execution reliable.
FlowEngine decides what happens next through RoutingStrategy.

Agent is a Stage.
Routing is what changes between Linear, Dynamic and Discussion.
