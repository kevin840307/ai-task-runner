AI Task Runner - Remaining Work
================================

Goal
----
Keep one small closed-loop runtime that is easy to understand, easy to extend with
new Stages, and reliable for 24H unattended execution.

Current architecture
--------------------

  UI / CLI / API / YAML List
              |
          RunRequest
              |
       WorkflowRunner
              |
          FlowEngine
         /         \
 StageExecutor    StateStore
       |
     Stage

One Workflow node = one Stage definition.
Workflow routing is only PASS / FAIL / ERROR result edges.

StageExecutor owns all technical reliability:
- unlimited technical retry when stage_retries = -1
- Same Session retry
- Fresh Session rotation
- transient API/backend retry with seconds-based delay/backoff
- timeout / safety / changed-file handling

Stage implementations do not own retry/recover/session logic.

UI workflow families
--------------------
1. Linear Workflow with Rollback / Loop - current production mode.
2. Dynamic Handoff - future; reuse the same Stage/StageExecutor/StateStore.
3. Discussion / Group Chat - future; participants remain Stages.

The user entry stays the same for every family: choose a Workflow/Profile in Chat,
enter the prompt, then run. Do not add a separate mode selector.


Current package layout
----------------------

runner/
  agent/       model client + backend adapters
  assets/      editable Workflow / Prompt assets
  config/      runtime configuration
  plugins/     extension discovery + runtime hooks/policies
  runtime/     process/state/supervisor reliability
  workflow/    graph loading, validation, routing and Stage execution
  api.py       public RunRequest entry
  script.py    YAML List adapter
  workspace.py project/workspace policy/context
  workflow_runner.py
  utils.py

Editable assets:

  runner/assets/
    workflows/*.yaml
    prompts/
      common/*.md
      ralphy/*.md
      workflow/*.md

Project-local assets use the same shape:

  <project>/.ai-task-runner/assets/
    workflows/*.yaml
    prompts/<category>/*.md

Folder review decision
----------------------

Do not merge the main domain folders further.

Keep:
- agent/      model/backend execution is one clear domain
- workflow/   graph + Stage semantics
- runtime/    durable/process reliability
- plugins/    optional extension/hook boundary
- assets/     user-editable Workflow/Prompt assets
- config/     runtime configuration

Do not merge just to reduce folder count.

Only merge a file when all of these are true:
1. it has one obvious owner;
2. it is mostly a thin helper/wrapper;
3. merging reduces navigation without creating a large mixed-responsibility file.

Current decisions:
- keep workflow/loader.py and workflow/schema.py separate: load/normalize vs validate
- keep plugins/registry.py and plugins/runtime.py separate: discovery/config vs hook runtime
- keep workflow_builder/publish.py and runner_control.py separate: explicit CLI/process boundaries
- keep agent provider adapters separate because Qwen/OpenCode are independently replaceable

Removed concepts must not return
--------------------------------
- execution_mode / RoutingStrategy hierarchy
- TaskRunner / Pipeline compatibility runtime
- recover / restart_at / repeat / max_attempts / on_exhausted
- repair Stage as a runtime concept
- hidden Plan Task/Review nodes
- plan_only runtime mode
- per-Stage retry policy
- System/Custom Workflow trees
- old runner/ai, runner/backends, runner/project, runner/utils package trees
- pre-assets Workflow/Prompt paths

Future - do not implement yet
-----------------------------

1. Dynamic Handoff
   - reuse the same Stage node
   - add only scheduler/handoff state when a real use case needs it
   - reuse StageExecutor / StateStore / plugins / Graph Designer

2. Discussion / Group Chat
   - participants/moderator/judge remain Stages
   - add only bounded round/order/termination state
   - reuse the same runtime and Graph Designer

3. Parallel
   - read-only Stages may eventually run concurrently
   - one writer per project/worktree by default
   - isolated worktrees required for parallel writers
   - do not build a generic DAG engine before a proven requirement

Final acceptance
----------------
The refactor is complete only when:
- adding a Stage requires work/result code only;
- rollback/loop is only a result edge;
- API/service failures can retry indefinitely with seconds-based delay;
- Workflow/Prompt assets use the structured assets layout;
- UI, CLI, API and YAML List execute the same runtime graph;
- Windows + Ubuntu CI pass;
- real-Qwen reliability probes pass;
- 24H soak passes without stuck state, orphan process or unbounded growth.
