AI Task Runner - Future Direction
=================================

Primary goal
------------
Keep the runtime intentionally small while preserving:

- 24H unattended execution
- durable resume
- closed-loop Stage routing
- custom Stages
- Plan/custom task producers
- n8n-style visual Workflow editing
- CLI execution
- YAML List batch execution
- future Dynamic/Parallel agents built from Stage

User-facing model
-----------------

All entry surfaces use the same Workflow model:

  n8n-style UI
       |
  CLI / API
       |
  YAML List
       |
       v
  RunRequest
       |
       v
  WorkflowRunner
       |
       v
  FlowEngine
     /      \
StageExecutor StateStore
     |
   Stage

UI, CLI and YAML List are adapters only.
They must never own their own routing or recovery semantics.

Core Workflow contract
----------------------

StageResult statuses:

  pass
  fail
  error

Default routing:

  pass  -> next
  fail  -> stop
  error -> stop

Optional result edge:

  routes:
    fail: execute

Targets:

  next
  done
  stop
  another unique Stage

Removed concepts must not return:

- execution_mode
- RoutingStrategy framework
- RecoveryPolicy
- SemanticRoutingPolicy
- LinearRouting compatibility wrapper
- TaskRunner alias
- Pipeline alias
- recover
- restart_at
- repeat
- max_attempts
- on_exhausted
- fresh_after_same_failures
- repair Stage as a runtime concept
- replan StageResult
- hidden __plan_task__ / __plan_review__
- plan_only runtime mode
- review-specific retry policy
- YAML List skip_on_max_cycles state

Stage model
-----------

Stage is the only execution/agent unit.

Built-ins remain small:
- base
- plan
- task
- review
- ai_validator
- command

Extensions use:

  register_stage(...)

Plan is simply a Stage that produces Task[].

Any custom Stage may also use:

  produces: tasks

No hidden Stage injection is allowed.

24H unattended contract
-----------------------

StageExecutor owns technical execution reliability:

- hooks / safety
- timeout
- backend execution
- same-session retry
- Fresh Session rotation
- changed-file tracking

One public retry concept:

  stage_retries: -1

Default -1 means:
- keep retrying technical Stage failures
- keep one Session bounded
- rotate Fresh Session periodically
- preserve current durable Workflow position

Deterministic configuration/state errors fail closed.

Outer run supervisor owns:
- transient service/backend restart
- resume from state.json
- unexpected Python exception logging
- repeated identical Python error fail-closed behavior

StateStore owns:
- one authoritative state.json
- atomic writes
- backup restore
- durable Workflow cursor
- task cursor
- latest StageResult
- completion state

No durable recovery state machine.

n8n-style UI
------------

The UI must be a visual editor for the exact runtime Workflow graph.

Node:
  Stage

Normal edge:
  PASS -> next

Explicit result edge:
  routes.pass
  routes.fail
  routes.error

Node settings:
- Stage type
- prompt/instructions
- role/session/tool/safety options
- scope: task
- validator/command options

Edge settings:
- result status
- target Stage / done / stop

Required behavior:
- drag Stage from catalog
- connect Stage nodes
- delete/reconnect edge
- edit node parameters in side panel
- System workflows read-only
- Custom/Project workflows editable
- save only after real loader/schema validation
- Dry Run uses the real FlowEngine
- no hidden nodes
- no retry/recovery edges

The UI and YAML are two views of the same graph.
A UI change must serialize to normal Workflow YAML.
A YAML change must render back to the same graph.

CLI
---

CLI remains a thin adapter.

Expected usage:

  select project
  select/provide workflow
  provide goal/prompt
  optional backend/runtime overrides
  run

No mode selector.

CLI must not contain routing behavior.
It creates RunRequest and calls the shared runtime.

YAML List
---------

YAML List is only a batch of RunRequests.

Each item may override:
- goal
- project_root / project_name
- workflow/workflow_file
- validator
- backend
- Stage retry/runtime timeout settings
- plugins

Each child uses:
- same Workflow loader
- same FlowEngine
- same StageExecutor
- same StateStore

YAML List does not get:
- custom routing semantics
- custom recovery state
- skip markers
- max-cycle policy

Future Dynamic Agent
--------------------

Do not build it yet.

When required, keep Stage unchanged.

Possible future scheduler:

  current Stage
      |
  StageResult + bounded handoff intent
      |
  DynamicScheduler
      |
  target Stage

Examples:
- Planner -> Coder
- Reviewer -> Coder
- Reviewer -> Architect
- Reviewer -> Researcher
- Validator -> done

Dynamic scheduling must reuse:
- StageExecutor
- StateStore
- Stage registry
- backend/session logic
- protected-file safety
- UI Stage catalog

Do not create a second Orchestrator.

UI direction for Dynamic:
- same Stage nodes
- allowed handoff edges/policies
- runtime current-owner highlight
- no separate product/editor

Future Parallel Agent
---------------------

Parallel execution also reuses Stage.

Default safety:
- read-only Stages may run concurrently
- only one writer per project/worktree
- parallel writers require isolated worktrees
- merge/reconcile is explicit

A future ParallelScheduler may coordinate ready Stages, but it must reuse the
same StageExecutor and StateStore.

UI direction for Parallel:
- same Stage nodes
- parallel branches
- write-ownership indication
- branch/join only when real requirements justify it

Do not pre-build a generic DAG engine now.

Non-goals
---------

Do not introduce unless a proven requirement needs them:
- UniversalAgent
- multiple full Orchestrators
- execution mode registries
- generic RoutingStrategy hierarchy
- arbitrary expression language
- unlimited DAG semantics
- large AgentMessage hierarchy
- separate UI per agent model
- duplicate CLI/YAML/UI runtimes

Final rule
----------

Workflow defines Stage nodes and result edges.
Stage performs one responsibility.
StageExecutor makes one Stage reliable.
FlowEngine moves through the graph.
StateStore makes progress resumable.

UI edits that graph.
CLI runs that graph.
YAML List batches runs of that graph.

Future Dynamic/Parallel behavior must reuse Stage.
