未來 UI 需求（架構契約）

目標：UI 是可整包移除的 Adapter；不能讓 Pipeline、StageExecutor、Stage、Workflow 依賴 UI。CLI / Skill / Python 的執行整合共用 runner.api，不建立第二套 retry / resume / validation；本機 detached UI 可完全不 import Runner Core，僅以 `.ai-task-runner` 的 runtime visibility files 讀取執行狀態與即時輸出。

1. CRUD Workflow
   - UI 修改的就是 Runner 真正使用的 Workflow 檔案，不建立 UI 專用 Workflow。
   - 使用 `runner.resources.read_text/delete` 與 `runner.workflow.loader.save_workflow`。
   - save 前走真正 Workflow parser/schema；使用 expected_hash 做 optimistic conflict detection，再 atomic replace。
   - 同一 Resource 的並行修改由 UI/backend caller serialize；Runner Core 不為尚未需要的 UI concurrency 增加 lock framework。
   - Active / Resume Run 使用自己的 durable snapshot（Workflow／Stage Prompt／Goal File／Final-AI Prompt）；UI 修改或刪除來源檔只影響下一個 Run。

2. Stage 使用 Python
   - 使用 `type: command`，Python script 與 File Validator 都走同一個 subprocess Stage。
   - Python 一律 subprocess 執行，不 import 任意使用者程式進 24H Runner process。
   - 新 behavior Stage 透過 Extension + Stage registry 擴充，Pipeline 不增加 Stage-name branch。

3. 修改 Skill / Prompt
   - 使用 `runner.resources.read_text/delete` 與 `runner.prompts.loader.save_prompt`。
   - Jinja syntax 驗證後才 atomic replace；active Run 使用自己的 frozen prompt/resource snapshot。
   - 同一 Prompt/Skill 的並行寫入同樣由 UI/backend caller serialize。

4. Project / Conversation UI
   - UI 可依 Project 建立 Conversation / Message / Run 關聯，類似 ChatGPT。
   - Project / Conversation / Message metadata 屬於 UI storage，不進 Runner Core / state.json。
   - 目前產品模型是一個 Project 同時間最多一個 Active Runtime；Conversation/Message 可以多筆，但不代表同 Project 內平行啟動多個 Runtime。
   - 本機 detached UI 不 import Runner Core；顯示目前執行狀態時讀取 `.ai-task-runner/state.json` 的必要欄位，顯示即時 Agent/subprocess 輸出時讀取 `.ai-task-runner/stream.log`，需要歷史診斷才讀 `log.txt` / `debug/`。
   - `stream.log` 是 bounded、可丟棄的 current-output visibility file；每個 subprocess 開始時清空，執行中持續覆寫最近輸出，不屬於 Resume state，也不可用來決定 PASS/FAIL、Retry、Session 或 routing。
   - Programmatic/remote integration 仍使用 `runner.api` event callback / `--json-events`；不要讓 detached UI 的檔案讀取取代正式執行 API。
   - 若未來真的需要多 Runtime，優先一個 Run 一個 worker process；不要只為 UI 增加 in-process global concurrency。
   - Stage/recover 的 structured feedback 使用 Core 既有 bounded `previous.data`；UI 不建立第二套 Stage data bus 或 recovery context。
   - FlowNode 的 `max_results` 直接沿用 Core Workflow schema/durable state；UI 只編輯該 opt-in 欄位，不建立 Grill/Challenge 專用 loop 或 counter。
   - FlowNode 的 `label` 直接沿用 Core Workflow metadata；UI 以 Stage `status` 顯示通用狀態、以 FlowNode `label` 顯示本次具體工作，不建立 UI 專用 status/label schema。
   - FlowNode 的 `fresh_after_same_failures` 直接沿用 Core semantic-dead-loop recovery；UI 只編輯這個 opt-in 欄位，不建立 Review 專用 Session/Retry 狀態機。

公開邊界：
- 執行：`runner.api`（`from runner.api import RunRequest, run`）
- 本機 detached UI runtime visibility：`.ai-task-runner/state.json`（唯讀必要欄位）+ `stream.log`（latest bounded output）+ `log.txt` / `debug/`（診斷）
- 編輯：`runner.resources` + domain owner；Stage metadata：`runner.workflow.registry`
- 擴充 Stage/Backend：ai_task_runner.extensions
- Runtime 橫切 Plugin：ai_task_runner.plugins

驗收：移除 UI package 後，現有 CLI、YAML List、24H retry/resume、Same/Fresh Session、Final Validator 行為完全不變。
