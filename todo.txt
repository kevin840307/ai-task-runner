AI Task Runner Refactor TODO
===========================

目標
----
在不破壞目前 Linear Workflow、24H 無人值守、Resume、YAML List、UI/CLI 相容性的前提下，
把核心整理成「Stage-centric + Single WorkflowRunner + Pluggable RoutingStrategy」。

未來長期支援：
1. Linear Workflow with Rollback / Loop
2. Multi-Agent with Dynamic Handoff
3. Multi-Agent Group Chat / Discussion

共同產品入口維持不變：
Chat / CLI / API -> 選 Workflow/Profile -> 輸入 Prompt -> Run

使用者不需要另外選 execution mode。
Workflow/Profile 自己描述 routing / execution semantics，UI 依 metadata 自動切換合適編輯方式。


最終核心模型
============

只保留少量、容易理解的核心概念：

1. Workflow
   - 定義有哪些 Stage
   - 定義 Edge / Routing 規則
   - 指定 RoutingStrategy
   - 保存 UI/editor metadata

2. Stage
   - 唯一執行單位
   - Plan / Execute / Review / Validator / Command / Tool / Agent 本質上都是 Stage
   - Agent 只是帶 role / prompt / session / tools 的 Stage
   - Stage 只執行工作並回 StageResult，不直接修改流程目的地

3. StageExecutor
   - 負責如何可靠執行一個 Stage
   - technical retry
   - timeout
   - watchdog
   - API transient recovery
   - same-session retry
   - fresh-session escalation
   - unexpected exception handling
   - protected-path safety
   - hooks / diagnostics

4. FlowEngine
   - 負責 StageResult 出來後下一步去哪裡
   - 使用 RoutingStrategy
   - 不執行 Agent 本身

5. RoutingStrategy
   - Linear
   - Dynamic
   - Discussion
   - 只處理 routing semantics，不複製 Runner / retry / session / watchdog

6. StateStore
   - durable state
   - checkpoint
   - resume
   - state migration
   - 保持單一 authoritative commit point

重要原則
========

- Stage 是唯一執行單位。
- Agent 不建立另一套平行 runtime；Agent 本質上就是 Stage。
- Stage 不決定 destination。
- Stage 可以回傳 routing intent / metadata，但 FlowEngine 最終決定是否允許及跳去哪裡。
- Retry / technical recover / timeout / watchdog / session recovery 是共用 Runtime 能力。
- Review FAIL / Validator FAIL / rollback / handoff / discussion round 是 Routing semantics。
- 不為 Linear、Dynamic、Discussion 各複製一套 Runner。
- 不建立 GenericEverything / UniversalGraph / UniversalAgent 等過度抽象。
- 先用第二種模式驗證抽象，再抽真正重複的部分。
- 優先讓人容易讀懂，再追求 pattern 漂亮。
- 少量、責任清楚的模組，優於大量 20~50 行小 class / 小檔案。

P0 - 現在優先重構
=================

[x] 1. 收斂成 Single WorkflowRunner
完成狀態：
- canonical runtime 已是 `WorkflowRunner`。
- `TaskRunner` 只剩 compatibility re-export。
- `execution_modes.py` 只保留目前 `linear` 的相容 metadata，不再持有 runner callback。

方向：
- TaskRunner 逐步收斂/改名為 WorkflowRunner。
- WorkflowRunner 共用：
  resource binding
  state load/save
  AI client setup
  StageContext
  StageExecutor
  FlowEngine
- 不建立 LinearWorkflowOrchestrator / DynamicHandoffOrchestrator / DiscussionOrchestrator 三套厚 runtime。
- mode 差異主要放在 RoutingStrategy。

驗收：
- 現有 Linear behavior 由跨平台 full pytest 保護。
- production bootstrap 只有一條 `WorkflowRunner` runtime path。
- 第二種 RoutingStrategy 尚未實作；未來不得複製 bootstrap / state / retry / session code。


[x] 2. 集中 Flow / Cursor 修改權
現況：
- Pipeline、RecoveryPolicy、rules.py 都會不同程度影響 workflow_position / task_step / replan / restart。
- 人讀 code 時需要在多個檔案拼出完整流程。

方向：
- 建立 FlowEngine（可從現有 Pipeline 漸進重構）。
- FlowEngine / RoutingStrategy 是唯一能決定 workflow destination 的地方。
- reducers 只更新 business/semantic state。
- StageExecutor 不決定 semantic destination。
- RecoveryPolicy 如果保留，只輸出 decision，不直接擁有 cursor。

驗收：
- workflow_position / task_step / next-stage mutation 只有 FlowEngine/RoutingStrategy owner。
- Review FAIL -> Execute
- Validator FAIL -> ordinary Stage
- Validator FAIL -> Planning
- recover edge
- repeat
- max_attempts
全部可從 routing code 一路看懂。


[x] 3. 明確區分 Technical Recovery 與 Semantic Routing
Technical Recovery（所有 routing strategy 共用）：
- API 429/502/503
- timeout
- Agent/CLI transient failure
- same-session retry
- fresh-session escalation
- expired session
- watchdog
- unexpected Python exception recovery
- bounded technical failure budget

Semantic Routing（FlowEngine 負責）：
- PASS / FAIL destination
- restart_at
- rollback
- recover edge
- replan
- handoff target
- discussion next speaker / next round

驗收：
- technical error 不會誤觸 Review/Validator semantic rollback。
- semantic FAIL 不會被 technical retry 當作 API failure 重試。
- tests/live 明確分成 technical fault 與 semantic FAIL。


[x] 4. Durable Transition Context / Resume Semantic Equivalence
現況：
- workflow_position / task_step durable。
- Pipeline 啟動時 previous StageResult 重新從 None 開始。
- process restart 後的 context 可能與不中斷執行不完全等價。

方向：
- 保存最小必要 transition context：
  source_stage
  status
  kind
  bounded output
  bounded structured data
- 不永久保存無限大的 StageResult。
- 定義 transition context clear rules，避免 stale feedback。

驗收：
- uninterrupted execution
  ==
  每個 Stage boundary kill + resume
  在 routing / control prompt / final artifact 上語意等價。
- real-Qwen resume probe 驗證。
- state 不會無限膨脹。


[ ] 5. 整理 RunState，但不要過度 class 化（刻意延後 schema migration）
現況：
- RunState 同時放：
  lifecycle
  tasks
  linear cursor
  validator feedback
  flow counters
  recovery counters
  session data

方向：
- 保持一個 durable state commit point。
- 邏輯上至少分成：
  common run state
  stage state
  routing_state
- routing_state 允許 strategy-specific data：
  Linear: position / task_step / task cursor
  Dynamic: current_stage / handoff counters
  Discussion: round / speaker / discussion state
- 不急著做三套大型 State class。
- serialization shape 等 ownership 穩定後再 migration。

驗收：
- 人看 state schema 能清楚知道欄位 owner。
- 舊 Linear state 可 migrate/resume。
- execution/routing strategy mismatch fail closed。


[x] 6. Stage Contract 統一
方向：
- Plan / Execute / Review / Validator / Agent 都遵守同一 Stage contract。
- Stage.run/context -> StageResult。
- Agent role/profile 不一定需要額外 subclass：
  role
  prompt
  session_key
  tools
  readonly/safety
可以由 AI Stage spec 配置。
- 避免 CoderAgentStage / ReviewerAgentStage / ArchitectAgentStage 無限制增加 class。

StageResult 原則：
- status 保持少量、穩定：
  pass / fail / error（必要時保留現有 replan 相容層）
- dynamic handoff intent 放 structured result/data。
- FlowEngine 驗證 routing intent 是否合法。

驗收：
- 新增一個新角色 Agent 通常只需要 config/spec，不需新增 runtime class。
- Stage 不直接 mutate workflow_position。

目標：

P0 - Human Maintainability / Code Readability
============================================

[x] 9. 過長檔案與過長函式瘦身（核心 + UI server 第一輪完成；live harness 模組化延後）
目的：
不是追求行數漂亮，而是降低閱讀時需要同時記住的事情。

優先檢查：
- runner/workflow/pipeline.py
- runner/workflow/stages.py
- runner/runtime/run_state.py
- runner/task_runner.py
- tool/qwen_live_reliability.py
- UI 大型 component / API module

拆分原則：
- 一個檔案只有一個主要 domain responsibility。
- 一個函式只做一段可命名流程。
- 超長測試工具可以按 probe/category 拆 module，但保留單一 CLI entry。
- 不要拆成大量只有 20~30 行、彼此跳來跳去的小檔案。

建議警戒線（不是硬性 lint）：
- production file > ~500 行：review 是否混了多個 responsibility。
- function > ~80 行：review 是否能抽明確 helper。
- class 同時處理 >=3 個 domain：優先檢查。
- nested branch >3~4 層：優先 early return / decision object。
- 相同 state mutation 出現在 >=2 modules：重新定義 owner。

驗收：
- 新人主要看 3~5 個核心檔案，可以理解：
  normal flow
  semantic rollback
  technical retry
  resume
  state save
- 不需要在 8~10 個 module 之間來回拼 execution flow。


[x] 10. 命名與檔案 responsibility 清理
重點：
- rules.py 名稱過泛，評估改成更精準名稱或拆出 reducer responsibility。
- RecoveryPolicy 名稱需避免 technical recovery / semantic recovery 混淆。
- TaskRunner 名稱與實際 workflow responsibility 不一致。
- Pipeline 最終若成為 FlowEngine，名稱應跟責任一致。

命名原則：
- technical retry/recovery 明確標 Technical。
- semantic routing/rollback 明確標 Routing/Transition。
- persistence 明確標 StateStore。
- 不使用 manager/helper/utils 作為大型 domain class 名稱，除非真的只是 generic helper。

驗收：
- 一件事情只有一條 production code path。
- contract tests 防止 legacy path 被重新使用。

最終完成定義
============

架構：
- 只有一套 WorkflowRunner。
- Stage 是唯一執行單位。
- Agent 只是 Stage 的配置/角色。
- StageExecutor 共用 retry/recover/timeout/session/watchdog。
- FlowEngine + RoutingStrategy 決定下一步。
- Linear / Dynamic / Discussion 不複製 runtime。

可維護性：
- 正常執行、rollback、technical retry、resume 都有單一清楚 owner。
- production code 沒有長期 old/new 雙路徑。
- 大型檔案只在確實需要時存在；超長函式被拆成有 domain 意義的步驟。
- 新人看 3~5 個核心 module 能理解主要 runtime。
- 名稱對應責任，不靠隱性 conventions。

可擴充性：
- 新增一般 Agent 角色，多數只需新增 Stage config/spec。
- 新增 Stage type 不需要修改 FlowEngine。
- 新增 RoutingStrategy 不需要複製 WorkflowRunner/StageExecutor。
- 未來新增第四種 workflow interaction model 時，優先新增 strategy/capability，而不是新 runtime。

UI：
- Chat 永遠：選 Workflow/Profile -> Prompt -> Run。
- Workflow/Profile metadata 決定 routing strategy 與 editor capability。
- 優先使用同一 Graph Designer。
- Linear / Dynamic / Discussion 透過 properties/edges/group settings 呈現差異。
- 切換 Workflow 不需要切換另一套產品入口或手動 mode selector。

Reliability：
- deterministic closure tests PASS。
- real-Qwen full-loop probes PASS。
- resume semantic equivalence PASS。
- 24H high-density soak PASS。
- 所有新 strategy 直接繼承現有 technical resilience，而不是重寫。
